# 数据清理发布与回滚

## 范围与检查

应用、监控 Worker 与 D1 必须同批发布。迁移 v1.25 将占位资源迁为明确网站账号关系；v1.26 删除旧字段、数量同步触发器、停用监控结构和历史 alertcfg。完整 SQL 与独立归档留在受保护的 backups 目录，不提交 GitHub。

本地演练命令：

```sh
python3 scripts/rehearse-cleanup.py --input backups/数据库导出.sql --output backups/新的演练目录
```

脚本完全在本地运行，输出 retired-values.json、upgraded.sqlite、逐表 report.json。检查原始关联与规范数量、电脑、金额、历史记录及归档数量，外键检查无错误，integrity_check=ok。新库与升级库的字段、外键、索引和触发器由迁移回归测试核对。Wrangler 本地 D1 另外运行两个 SQL 迁移验证。

## 发布步骤

1. 完成各批构建、清理、类型、Node 和浏览器回归；检查最终差异与敏感数据。
2. 记录生产 Pages 部署和 Worker 版本；启用维护响应，暂停自动监控。等待已有检查结束。
3. 重新导出生产 SQL，立即在副本运行演练，保存独立旧值归档和逐表报告。
4. 在同一维护窗口顺序执行两个迁移；核对表数量、关键记录、外键和旧结构已移除。
5. 推送配套 GitHub 版本并发布 Pages、Worker。确认 Pages 实际关联的提交和数据库版本一致，恢复巡检。
6. 检查登录、网站总表、账号关系、监控、备份、图标和复制资料。普通读取不泄露完整 Token。

## 恢复步骤

若数据库升级或生产行为失败，继续维护并保持监控暂停。使用迁移前完整 SQL 恢复数据库，再恢复记录的 Pages 与 Worker 配套版本，验证外键、登录、网站及域名数量和巡检后才恢复访问。不可只回滚前端而保留不匹配的数据库。

本地 SQL 恢复演练使用另一个空数据库导入迁移前 SQL，核对全部原始表及记录数。生产恢复必须在维护状态处理目标应用数据，保留 Cloudflare 内部表；恢复前留存失败状态 SQL 以供分析。
